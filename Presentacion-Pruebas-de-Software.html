La idea que amarra todo: no son técnicas que compiten. Son capas de una misma red de seguridad. Una pirámide sana tiene muchas unitarias rápidas, algunas de integración y muy pocas de punta a punta.

Contexto

Un bug cuesta distinto según cuándo lo encuentras

Un error en la lógica de negocio no nace caro: nace gratis. Se encarece con cada etapa que atraviesa sin que nadie lo note. Por eso las pruebas se automatizan y se ejecutan en cada cambio, no al final del proyecto.

  • Lo encuentras escribiendo el test: lo corriges en minutos, con el código aún fresco en la cabeza.
  • Lo encuentra el QA: hay que reproducirlo, entenderlo, reabrirlo en el tablero, volver a desplegar.
  • Lo encuentra el usuario: hay incidente, hay pérdida de datos, hay confianza rota y hay una reunión incómoda.

Si algo es imposible de testear, casi siempre es porque está mal acoplado. El test es el primer crítico de tu diseño.

Haz clic en cada capa

¿Por qué más abajo hay más?

Porque son baratas de escribir y de ejecutar. Mil pruebas unitarias corren en segundos; mil pruebas E2E tardarían horas y fallarían por razones ajenas al código.

El antipatrón: el cono de helado

Pirámide invertida: muchas E2E y casi nada unitario. Resultado: suite lenta, inestable y que nadie se atreve a tocar. Es el error más común en equipos que empiezan.

Las capas no se sustituyen

Una prueba unitaria perfecta no te dice que el JSON salga bien por HTTP. Cada capa cubre un riesgo distinto; por eso en clase hicimos las tres.

Lo que sí distingue a BDD

No es «Cucumber». BDD es una forma de acordar el comportamiento antes de programarlo: negocio escribe el escenario en lenguaje natural, desarrollo lo automatiza. Cucumber es solo la herramienta que une ambas mitades.

Lo que BDD no es

No es una capa más de pruebas unitarias disfrazada de inglés. Si escribes escenarios Gherkin para probar getters y setters, terminaste con lo peor de los dos mundos: lento y redundante.

Estructura

Todo test sano tiene las mismas tres partes

Se conoce como AAA (Arrange–Act–Assert) y es el mismo esqueleto de Gherkin. Un test que mezcla las tres partes en diez líneas no se entiende cuando falla.

1 · ARRANGE
Prepara el escenarioCreas los objetos, defines los datos de entrada, configuras los mocks. Todo lo que el test necesita para poder ejecutarse.
2 · ACT
Ejecuta la acciónUna sola llamada al método que estás probando. Si aquí hay tres llamadas, probablemente tienes tres tests disfrazados de uno.
3 · ASSERT
Verifica el resultadoCompara lo obtenido con lo esperado. Si no hay aserción, no es un test: es un script que a veces explota.
SumaTest.javaTema 1
@Test
public void sumaPositivos() {
  // ARRANGE — preparo los datos
  Suma S = new Suma(2, 3);

  // ACT — ejecuto lo que quiero probar
  int resultado = S.sumar();

  // ASSERT — verifico
  assertTrue(resultado == 5);
}

Observa el detalle: en el proyecto original la llamada va dentro del assertTrue. Funciona, pero separar Arrange/Act/Assert hace que el test se lea como una receta. Lo retomamos en la diapositiva de hallazgos.

Aplicación real · Tema 1

Empezamos por lo más simple: sumar

Antes de Spring, antes de APIs, la clase más pequeña del curso. El objetivo no era el cálculo: era aprender el ciclo completo — escribo, ejecuto, veo verde o rojo.

Suma.javaproducción
public class Suma {
  private int a, b;

  public Suma(int a, int b) {
    this.a = a;
    this.b = b;
  }

  public int sumar() {
    return a + b;
  }
}

El valor de esta prueba no es demostrar que 2+3=5. Es demostrar que el mecanismo funciona: Maven descubre el test, lo ejecuta y reporta. Una vez que ese circuito gira, escalar a lógica compleja es solo cuestión de escribir más casos.

El caso clásico de la caja blanca

Tres lados entran, un número sale: 0 no existe, 1 equilátero, 2 isósceles, 3 escaleno. Mueve los valores y observa la misma lógica real de Triangulo.java.

Triangulo.javadesigualdad triangular
public boolean validarTriangulo(){
  if ((lado1 < (lado2+lado3)) && (lado1 > Math.abs(lado2-lado3))) {
    if ((lado2 < (lado1+lado3)) && (lado2 > Math.abs(lado1-lado3))) {
      if ((lado3 < (lado1+lado2)) && (lado3 > Math.abs(lado1-lado2))) {
        return true;   // cada lado debe ser menor
      }                // que la suma de los otros dos
    }                  // y mayor que su diferencia
  }
  return false;
}

Por qué este ejercicio enseña tanto: la lógica tiene cuatro salidas posibles y varias formas de entrar a cada una. Aquí nacen conceptos como cobertura de ramas y valores límite. Prueba 1 · 2 · 10: la suma de dos lados no alcanza al tercero, así que el triángulo no cierra — y el método devuelve 0.

Los 6 casos del test: 4 000 · 30 000 · 50 000 · 120 000 · 200 000 · 300 000. Cada uno cae en un tramo distinto. Ese es el valor real de la prueba: no verifica «un número», verifica cada frontera de la regla de negocio.

ImpuestoRenta.javafragmento
private double uit = 3950;

public double calcularImpuesto() {
  double iR;

  if (sueldo < (uit * 7)) {
    return iR = 0;
  } else if (sueldo <= (uit * 12)) {
    excedente = sueldo - (uit * 7);
    iR = excedente * 0.08;
    return iR;
  } else if (sueldo <= (uit * 27)) {
    excedente = sueldo - (uit * 12);
    iR = excedente * 0.14
       + uit * 5 * 0.08;  <-- acumulado
    return iR;
  }
  // ... 17 %, 20 % y 30 % siguen el mismo patrón
}

La trampa del test que pasó por casualidad. En tasa8True() se espera 188.00 para un sueldo de 30 000: (30000 − 27650) × 0.08 = 188. Pero el test usa assertTrue(calcularImpuesto() == 188.00) con un double. Comparar flotantes con == es frágil: por eso se recalcula con Math.rint(...*100)/100 antes de comparar. Funciona, pero es un parche — el delta es la solución correcta.

Aplicación real · Tema 2

El mejor ejemplo de @BeforeEach del curso

ShoppingCartTest prueba cinco comportamientos del carrito. Los cinco necesitan un carrito con un producto dentro — pero cada test debe empezar de cero.

ShoppingCartTest.javael patrón correcto
@BeforeEach
void setUp() throws Exception {
  cart1 = new ShoppingCart();
  prod1 = new Product("P001", "Plasma TV LG 32",
                 "Plasma TV with TDT Decod...", 699.99);
  cart1.addItem(prod1);      // estado base
}

@AfterEach
void tearDown() {
  cart1 = null;                 // libera referencias
  prod1 = null;
}

@Test
public void testAddItem() {
  Product prod2 = new Product("P002", "DVD player",
                              "DVD player with remote...", 39.99);
  cart1.addItem(prod2);       // parte de 1, queda en 2

  assertEquals(2, cart1.getItemCount());
  double esperado = prod1.getPrice() + prod2.getPrice();
  assertEquals(esperado, cart1.getBalance());
}
Secuencia real de ejecución
@BeforeAll
1 vezImprime el mensaje. No crea nada porque el carrito debe ser nuevo en cada test.
@BeforeEach
5 vecesUn carrito limpio con 1 producto, para cada uno de los 5 tests.
@Test
5 vecesgetBalance · addItem · getItemCount · removeItem · empty.

5 vecesAnula las referencias. Aquí no hace falta, pero el hábito es bueno.

Si no existiera @BeforeEach: el test de removeItem vaciaría el carrito y el de getItemCount fallaría al ejecutarse después. El orden de ejecución de JUnit no está garantizado — el aislamiento no es opcional.

Mirada crítica

Los tests del curso, examinados sin piedad

Los proyectos cumplen su función didáctica, pero tienen patrones que en un proyecto real conviene corregir. Reconocerlos es parte de aprender a probar.

Redundancia

Tres tests para una sola verdad

tasa8True, tasa8False y tasa8Equals verifican exactamente lo mismo con tres sintaxis distintas:

assertTrue(imp() == 188.00);
assertFalse(imp() != 188.00);   // la negación de lo mismo
assertEquals(imp(), 188.00);    // la forma idiomática

Costo: 18 tests donde bastaban 6. Si cambia la tasa, hay que editar 18 sitios. Si uno falla, el reporte dice lo mismo tres veces.

Nombres

Los métodos no se nombran test1…test6

YearUtilitiesTest tiene test1() a test6(). Cuando uno falla en CI, el reporte dice «test4 falló» y nadie sabe qué regla se rompió.

esBisiesto_anioDivisiblePor400_retornaTrue()
esBisiesto_anioDivisiblePor100NoPor400_retornaFalse()

Con @DisplayName("Año 400 es bisiesto") el reporte se lee como una especificación.

Flotantes

Comparar doubles con ==

assertTrue(calcularImpuesto() == 188.00) puede fallar por representación binaria. El código lo mitiga con Math.rint(x*100)/100, que funciona para este caso pero no es la solución general.

La forma correcta: assertEquals(188.00, impuesto, 0.01) — el tercer argumento es la tolerancia aceptada.

Anotación mal usada

@WebMvcTest sobre un test de servicio

PersonaServiceImplTest está anotado con @WebMvcTest(PersonaServiceImplTest.class). Esa anotación levanta un contexto web de Spring y no tiene sentido para probar un servicio con mocks manuales.

Efecto: arranque más lento y un contexto que puede fallar por razones ajenas al test. Para pruebas con Mockito puro no se necesita ninguna anotación de Spring.

Conclusión honesta: estos detalles no invalidan el aprendizaje — el mecanismo se entendió y se aplicó. Pero en un proyecto productivo, la diferencia entre «tengo tests» y «tengo tests que me sirven» está justo en estos detalles. Cantidad no es calidad.

02
Dobles de prueba

Mockito

Cuando la unidad necesita a alguien más para funcionar, se le da un doble: un objeto que responde lo que el test decide, sin tocar la base de datos.

@Mock @InjectMocks when · thenReturn verify
Fundamento

No todos los dobles son iguales

«Mock» se usa como término paraguas, pero los dobles de prueba tienen cinco sabores. Confundirlos lleva a tests que verifican cosas equivocadas.

Dummy

Relleno

Se pasa porque la firma lo exige, pero nunca se usa. No responde nada.

new Persona() // solo para el parámetro
Stub

Responde, no verifica

Devuelve datos prefabricados. Es exactamente lo que hace when(...).thenReturn(...).

when(repo.findAll())
  .thenReturn(lista)
Spy

Objeto real, espiado

Usa el código real, pero puedes sustituir o registrar llamadas concretas. Se usa poco: suele indicar mal diseño.

spy(new Carrito())
Mock

Responde y verifica

Un doble con expectativas. Se le programa la respuesta y luego se comprueba si fue llamado, cuántas veces y con qué argumentos.

verify(service, times(1))
  .eliminarPersona(1)
Fake

Implementación simplificada

Tiene código real pero ligero: una lista en memoria que hace de repositorio. No lo genera Mockito; lo escribes tú.

InMemoryPersonaRepo
En clase

Qué usamos

@Mock para el repositorio (stub con when) y verify para comprobar la interacción en el test del controlador. Los dos extremos del espectro.

La regla que evita tests frágiles: verifica comportamiento observable, no implementación. Un test que hace verify de cinco llamadas internas se rompe en cuanto refactorizas, aunque el resultado siga siendo correcto. Usa verify solo cuando el efecto es la interacción (enviar un correo, borrar un registro).

El servicio de personas necesita un repositorio. En producción ese repositorio habla con SQL Server; en el test es un doble que devuelve una lista en memoria.

Qué está pasando

Beneficio concreto: este test corre sin SQL Server, sin driver JDBC y sin datos. Se puede ejecutar en un portátil sin red y en un pipeline de CI en 200 ms. La lógica del servicio queda verificada de forma determinista.

@Mock

Crea el doble. Nunca ejecuta código real.

@InjectMocks

Crea el objeto real e inyecta los mocks en sus dependencias.

@ExtendWith

Sin ella, las anotaciones no hacen nada: el runner de Mockito debe activarse.

API de Mockito

when · thenReturn · verify · doNothing

Todo Mockito cabe en cuatro ideas. El resto es sintaxis.

Stubbing — programar la respuesta
// devuelve un valor fijo
when(repo.findAll()).thenReturn(personas);

// cualquier Integer que llegue
when(repo.findById(anyInt()))
    .thenReturn(Optional.of(persona));

// cualquier Persona
when(repo.save(any(Persona.class)))
    .thenReturn(persona);

// método void: no devuelve nada
doNothing().when(repo).deleteById(anyInt());
Verification — comprobar la interacción
// ¿se llamó exactamente una vez?
verify(personaService, times(1))
    .eliminarPersona(anyInt());

// ¿no se llamó nunca?
verify(repo, never()).deleteById(anyInt());

// con argumento concreto
verify(repo).findById(1);

// ¿cuántas veces?
verify(repo, times(2)).save(any());

El caso real: PersonaControllerTest

Aquí se mockea el servicio para probar el controlador aislado. El test de borrado es el ejemplo más claro de verificación de interacción:

@Test
void eliminarPersona() {
  when(personaServiceImpl.eliminarPersona(anyInt()))
      .thenReturn("Persona eliminada");

  personaController.eliminarPersona(1);

  verify(personaServiceImpl, times(1))
      .eliminarPersona(anyInt());
}

No se verifica el cuerpo de la respuesta: se verifica que el controlador delegó. Es correcto aquí porque el controlador no tiene lógica propia que probar.

Lo que falta en el código del curso

Mocks preparados con when que nunca se usan (en listarPersonas del controlador sí se usan, pero en otros métodos sobra preparación). Cada when innecesario es ruido que oculta la intención del test.

Cuándo NO usar Mockito

  • Para mockear clases que tú controlas y son triviales: usa el objeto real.
  • Para mockear tipos del JDK (List, String): usa un valor real.
  • Para «arreglar» un diseño acoplado: el mock esconde el problema, no lo resuelve.
Transición

Con todo en verde, la app puede estar rota

Este es el momento donde la siguiente técnica se vuelve inevitable. Una suite unitaria perfecta no garantiza que el sistema funcione.

Lo que sí demuestra

  • Que calcularImpuesto() devuelve el número correcto para cada tramo.
  • Que el carrito suma bien los precios.
  • Que el servicio devuelve lo que el repositorio le entrega.
  • Que un refactor no cambió el comportamiento interno.

Lo que no puede demostrar

  • Que el endpoint responda en /api/v1/persona y no en otra ruta.
  • Que Spring serialice bien el objeto a JSON.
  • Que la consulta JPA sea válida contra la base real.
  • Que el contrato acordado con el frontend se respete.
  • Que un API externo siga devolviendo lo que esperas.

El mock es el punto ciego. Cuando hicimos when(repo.findById(anyInt())).thenReturn(Optional.of(persona)), le dijimos al sistema qué responder. Si el repositorio real tiene un error de SQL, si la entidad tiene mal el mapeo o si la base no existe — el test sigue en verde. Probamos la lógica de nuestro código, no la realidad del sistema.

03
Pruebas de integración

Rest Assured

Se deja de suponer y se hace la llamada de verdad: HTTP real, servidor real, JSON real. La prueba se escribe con la misma estructura Given / When / Then que ya conocemos.

given() when() then() JSON Schema Hamcrest matchers
Fundamento

Integración = varias piezas, juntas, de verdad

La prueba unitaria aísla; la de integración conecta. Su valor está justo en lo que la unitaria no puede ver: el cableado entre componentes.

Nivel 1

Capas internas

Controlador → servicio → repositorio → base de datos, reales. Se usa @SpringBootTest con MockMvc o Testcontainers.

Verifica que el mapeo JPA y las rutas funcionan.

Nivel 2

API por HTTP

Un cliente HTTP hace la petición real contra un servidor levantado. Se usa Rest Assured. Es el nivel que trabajamos en el Tema 4.

Verifica el contrato: ruta, status, cuerpo, tipos.

Nivel 3

Servicios externos

Se consume un API de terceros real: Zippopotam, GoRest. Es lo que hicimos, y es la variante más frágil.

Verifica que la integración con el proveedor sigue viva.

¿Por qué no todo son pruebas de integración?

  • Son lentas: decenas o cientos de veces más que una unitaria.
  • Son frágiles: fallan por red, por el servidor de terceros, por un certificado vencido.
  • Diagnostican peor: cuando fallan, no sabes qué capa rompió.
  • Dependen del entorno: un API público puede cambiar sin avisarte.

El riesgo real de probar APIs de terceros

En el Tema 4 llamamos a http://api.zippopotam.us y a https://gorest.co.in. Si mañana el servicio cae, cambia su contrato o limita el rate, nuestra suite falla sin que hayamos tocado una línea de código.

Mitigaciones: grabar las respuestas (VCR/record-playback), levantar un stub local con WireMock, o marcar esos tests como @Tag("external") y excluirlos del pipeline obligatorio.

Aplicación real

Una petición HTTP escrita como una frase

Rest Assured propone leer el test en voz alta: «dado que apunto a este endpoint con estos parámetros, cuando hago GET, entonces espero un 200 con este cuerpo». Construye la llamada y envíala.

País
Código postal

El endpoint real: http://api.zippopotam.us/{pais}/{codigopostal}. Sin API key, sin registro. Devuelve el país y los nombres de lugar asociados al código postal.

SerenityRest.given() .baseUri("http://api.zippopotam.us") .when().get() .then().statusCode(200)
  .body("country", equalTo("United States"))
  .body("'places'[0].'place name'", equalTo("New York City"));

given()

Prepara: URL base, parámetros, headers, autenticación, body.

when()

Ejecuta: get, post, put, delete.

then()

Verifica: status, headers, cuerpo con matchers de Hamcrest.

@When("Busco un código postal {word} para el codigo de pais {word}")

public void ubicacionDeberiaSer(String ubicacion, String pais) {

  restAssuredThat(r -> r.body(UbicacionResponse.PAIS,

}

Aplicación real · Tema4Ejercicio2

No basta con que responda 200

Un API puede devolver 200 con un cuerpo completamente distinto al acordado. El esquema JSON convierte el contrato en algo verificable automáticamente.

ResponseUserSchemaValid.jsoncontrato
{
  "$schema": "http://json-schema.org/draft-04/schema#",
  "type": "array",
  "items": [{
    "type": "object",
    "properties": {
      "id":     { "type": "integer" },
      "name":   { "type": "string" },
      "email":  { "type": "string" },
      "gender": { "type": "string" },
      "status": { "type": "string" }
    },
    "required": ["id","name","email","gender","status"]
  }]
}
cómo se usa
File jsonSchema = new File(
    Constantes.JSON_SCHEMA + "/ResponseUserSchemaValid.json");

SerenityRest.then()
    .assertThat()
    .body(JsonSchemaValidator
        .matchesJsonSchema(jsonSchema));

Qué gana el equipo con esto

  • El contrato queda escrito y versionado en el repo.
  • Si el proveedor renombra un campo, el test falla con el nombre exacto.
  • El frontend puede consumir el mismo esquema para tipar.

Dos matices del caso real

1. El esquema declara "type": "array", así que solo valida correctamente si el API devuelve una lista. En obtener_usuario.feature el endpoint /public/v2/users devuelve lista — coherente.

2. required exige los cinco campos. Si GoRest añade uno nuevo, el test sigue pasando: el esquema no prohíbe campos extra.

04
Automatización BDD

Gherkin + Cucumber

El comportamiento se escribe en un lenguaje que negocio puede leer, y ese mismo texto se ejecuta como prueba automática. Sin traducciones manuales, sin malentendidos.

Feature Scenario Given / When / Then Scenario Outline Serenity
Fundamento

Cinco palabras que estructuran todo

Gherkin es un lenguaje de palabras clave. No es código: no tiene variables, ni bucles, ni condicionales. Y eso es intencional — su lector principal es una persona.

Feature
La funcionalidadUna capacidad del sistema, descrita en una línea. Agrupa escenarios relacionados.
Scenario
Un caso concretoUna situación que se puede verificar de principio a fin.
Given
El contextoEl estado del mundo antes de actuar. Precondición. Equivale a Arrange.
When
La acciónLo que dispara el comportamiento. Un solo evento. Equivale a Act.
Then
El resultadoEl resultado observable esperado. Equivale a Assert.

Y & But (And/Pero) continúan el paso anterior sin repetir la palabra clave. Background pone pasos comunes a todos los escenarios de una feature.

    And validar el usuario de la lista de esquemas json

  Scenario Outline: Obtener usuario con parametro de estado
    Given el usuario con estado "<estatus>"

    And validar el estado del usuario debe ser "<estatus>"

    Examples:
      | estatus  |

Detalle clave: el texto entre "..." es un parámetro. En el StepDef se recibe como String y se inyecta en la petición. Sin esa comilla, Cucumber no sabe qué parte del paso es variable.

Cada paso busca su método por coincidencia

Pasa el cursor sobre un paso del .feature: Cucumber hace exactamente lo mismo — busca un StepDef cuya anotación coincida con el texto y le inyecta los parámetros.

Aplicación real · Tema4Ejercicio2

Cinco escenarios, cuatro filtros, un solo endpoint

Este ejercicio combina las tres técnicas: BDD describe, Rest Assured ejecuta, JSON Schema valida el contrato. El endpoint es https://gorest.co.in/public/v2/users.

UsuarioAPI.javacapa de interacción
public static String GET_USER =
    Constantes.BASE_URL + "/public/v2/users";

@Step("Get user")
public void obtenerUSuarios(String nombre, String email,
                              String genero, String estado) {
  SerenityRest.given()
      .queryParam("name",   nombre)
      .queryParam("email",  email)
      .queryParam("gender", genero)
      .queryParam("status", estado);
}

Observa el patrón: siempre se envían los cuatro queryParam, aunque tres vayan vacíos. Es una decisión defendible (uniformidad) pero genera URLs como ?name=&email=&gender=male&status=. Muchos APIs interpretan el parámetro vacío como filtro activo. Una alternativa más limpia: enviar solo el que tiene valor.

Un problema real del proyecto: el @Test del feature es una etiqueta de filtro, no de JUnit. Y el obtener_usuario.feature tiene pasos When/Then que dependen del orden de ejecución de los Scenario Outline. Si Cucumber ejecutara en paralelo, el estado compartido de SerenityRest se rompería. Es una limitación conocida del enfoque de estado estático.

Decisión

El criterio para elegir

No se elige por moda: se elige por dónde está el riesgo. Si el riesgo es un cálculo, unitaria. Si es el cableado, integración. Si es un malentendido con negocio, BDD.

SituaciónTécnica adecuadaPor qué
Una fórmula tributaria con seis tramosUnitaria · JUnitEs lógica pura, determinista, sin dependencias. Rápida y exhaustiva.
Un servicio que consulta tres tablasUnitaria · JUnit + MockitoSe mockea el repositorio para probar la lógica de composición sin tocar la BD.
Un endpoint nuevo del backendIntegración · Rest AssuredHay que verificar ruta, status, serialización y contrato, no solo la lógica.
Un contrato con un proveedor externoIntegración + JSON SchemaEl riesgo es que el otro cambie. El esquema lo detecta con nombre y apellido.
Una regla de negocio que negocio redactóBDD · GherkinEl escenario es el acuerdo. Si el test falla, falló el acuerdo o la implementación — ambos importan.
El flujo de compra completoE2E · UISolo aquí se puede confirmar que el usuario real termina la compra. Una o dos pruebas, no cincuenta.
Regla 1

Prueba en el nivel más bajo posible

Si puedes demostrarlo con una unitaria, no escribas una de integración. Cada nivel hacia arriba cuesta más y dice menos.

Regla 2

Un test, una razón para fallar

Si un test falla por cinco motivos posibles, no te está informando: te está obligando a investigar.

Regla 3

Si duele mantenerlo, está mal escrito

Un test que se rompe en cada refactor no protege: extorsiona. Ese olor indica que estás probando implementación, no comportamiento.

Cinco preguntas rápidas

Elige una opción en cada tarjeta. La respuesta se revela al instante.

Para llevarse

Diez reglas que sobreviven al curso

  • Un test = una razón para fallar. Si falla, debe quedar claro qué se rompió.
  • Nombre el test por el comportamiento, no por el método. esBisiesto_400_retornaTrue, no test4.
  • Arrange · Act · Assert separados y visibles. Se lee como una receta.
  • Aísla con el ciclo de vida. @BeforeEach existe para que el orden no importe.
  • Verifica comportamiento, no implementación. verify solo cuando la interacción es el resultado.
  • No mockees lo que no necesitas. Cada doble innecesario es una mentira más en el test.
  • Para doubles usa delta, nunca ==. assertEquals(esperado, real, 0.01).
  • El esquema JSON es parte del contrato. Versionado en el repo, igual que el código.
  • Los APIs de terceros no son tu entorno de pruebas. Stub o graba las respuestas.
  • Cobertura no es calidad. Puedes cubrir el 100 % de las líneas sin probar una sola regla de negocio.

La idea final. Probar no es una fase al final del proyecto ni una tarea del QA. Es la forma de saber —no de creer— que el software hace lo que dice hacer. Las tres técnicas que vimos no compiten entre sí: se apilan. JUnit te dice que cada pieza calcula bien. Rest Assured te dice que las piezas conectadas responden bien. Gherkin y Cucumber te dicen que lo que responden es lo que el negocio pidió. Sin las tres, siempre queda una pregunta sin responder.
